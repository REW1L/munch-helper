# Story 6.7: Room History View Shows Battle Events and Opens Completed Battles

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a player,
I want to review battle-related room history entries and open completed battle details,
so that I can understand battle outcomes and revisit the full record when needed.

## Acceptance Criteria

1. **Given** a `battle_started` entry (`eventType === 'battle_started'`), **when** it is displayed in the room history list, **then** the `LogEntry` row shows a **battle glyph** (`⚔️`) in place of the character avatar, the **battle name** from `payload.battle.name` (fallback to the entry's `summary` text if `payload.battle.name` is missing/empty), a **"started"** label, and the relative-time stamp produced by Story 6.6's `formatRelativeTime` helper — and the row is **non-interactive** (no drill-in: it does not produce an `onPress` callback, and its `accessibilityRole` is **not** `button`).
2. **Given** a `battle_concluded` entry (`eventType === 'battle_concluded'`), **when** it is displayed, **then** the row shows the battle glyph, the battle name (or `summary` fallback), a **result chip** that reads **`"Players Win"`** when `payload.battle.result === 'players_win'`, **`"Monster Wins"`** when `payload.battle.result === 'monster_wins'`, or the neutral label **`"Concluded"`** when `result` is missing/`null`/unknown — colored `AppTheme.colors.accent` for `players_win`, `AppTheme.colors.danger` for `monster_wins`, `AppTheme.colors.textMuted` for the neutral fallback — and the row is **tappable** (renders a `Pressable`/`TouchableOpacity` with `accessibilityRole="button"`, `onPress` fires the drill-in for this entry).
3. **Given** a `battle_discarded` entry (`eventType === 'battle_discarded'`), **when** it is displayed, **then** the row shows the battle glyph, the battle name (or `summary` fallback), a **"discarded"** label colored `AppTheme.colors.textMuted`, and the row is **tappable** (drill-in shows the participation snapshot — no result chip, since a discarded battle has no result).
4. **Given** a tappable battle entry (`battle_concluded` or `battle_discarded`) **with** a usable `payload.battle` object (an object with at least `id` and at least one of `name` / `playerSide` / `monsterSide` present), **when** I tap it, **then** an **in-place `BattleHistoryModal` overlay opens on the Room History screen** rendering the **full battle record** from `payload.battle` (no network fetch) — see AC 6 for contents.
5. **Given** a `battle_concluded` or `battle_discarded` entry whose `payload.battle` is **absent, null, non-object, or carries no usable record fields** (no `name`/`playerSide`/`monsterSide`), **when** the row is displayed, **then** the entry is shown as **non-interactive** rather than failing silently — the row does not render as a `Pressable`/`TouchableOpacity`, its `accessibilityRole` is **not** `button`, and tapping the row area produces **no** `onPress` and **no** modal. (Renders the same neutral visual styling as a tappable entry minus the press affordance; never crashes; never opens an empty modal.)
6. **Given** the `BattleHistoryModal` is open for an entry, **when** it renders, **then** it shows: (a) the **battle name** (`payload.battle.name`, fallback `summary` text); (b) the **status** label (`payload.battle.status` — capitalised "Concluded"/"Discarded"); (c) the **result** for `battle_concluded` (Players Win / Monster Wins / "—" if missing) colored per AC 2 — omitted for `battle_discarded`; (d) the **Player Side** participants — for each id in `payload.battle.playerSide.characterIds`, look up the character via `useRoomCharacters(roomId)` and render its name (and, if available, level + power); **unresolved ids** (character was removed since, or characters list still loading) render the neutral label **`"Removed character"`** (never blank, never crash, no outbound HTTP fetch to resolve names — ADR-11); (e) the **Player Side bonuses** (`playerSide.bonuses[].value` rendered with sign, e.g. `+5` / `-2`); (f) the **Monster Side** monsters (`monsterSide.monsters[].name` + `level`); (g) the **Monster Side bonuses** (signed); (h) the **occurredAt** rendered as the same relative-time idiom (`formatRelativeTime`); (i) a visible **close affordance** (top-right close button with `accessibilityLabel="Close battle history"`, `accessibilityRole="button"`).
7. **Given** the `BattleHistoryModal` is open, **when** the user dismisses it via the close button **or** via the platform back gesture (RN `Modal` `onRequestClose`), **then** the modal closes and the Room History list is restored to its previous scroll position with no entries duplicated, re-fetched, or removed — modal open/close must **not** invalidate, refetch, or mutate the `useRoomLogs` query state.
8. **Given** I navigate away from the Room History screen (back to the Room View) while the modal is **open** or **closed**, **when** I return to the Room History screen, **then** the modal is **not** persisted open across screen mounts (it starts closed), the room history list state is governed entirely by `useRoomLogs` (Story 6.5), and no battle modal artifact remains in the DOM/tree.
9. **Given** accessibility, **when** a tappable battle entry row renders, **then** the row exposes a single descriptive `accessibilityLabel` on the press container — concluded: `"Battle <name>, <result phrase>, <relative time>. Double-tap to open battle record."`; discarded: `"Battle <name>, discarded, <relative time>. Double-tap to open battle record."`; **and** non-interactive `battle_started` (AC 1) / non-interactive incomplete-payload (AC 5): `"Battle <name>, <status phrase>, <relative time>."` with **no** "Double-tap" hint and **no** `accessibilityRole="button"`. The battle glyph `Text`/`Image` is hidden from a11y (it must not double-announce, mirroring Story 6.6's avatar treatment).
10. **Given** the quality gate, **when** `npm test` / `npm run test:coverage` run from `frontend/`, **then** the co-located `components/munchkin/LogEntry.test.tsx` (extended) and a new `components/munchkin/BattleHistoryModal.test.tsx` are discovered by the default `vitest.config.ts` (`include: ['**/*.test.{ts,tsx}']`, jsdom) and the **70% line floor still passes** (do not lower it); tests assert real behavior — each battle variant's row content + interactivity (started non-tappable; concluded/discarded tappable with the right result/discarded chip), tap fires `onPress(entry)` only for completed entries with a usable `payload.battle`, incomplete-payload concluded/discarded entries are non-interactive (no `onPress`, no `accessibilityRole="button"`), the modal renders battle name/status/result/participants/bonuses/timestamp from a fixture payload, unresolved character ids fall back to `"Removed character"` without crashing, close button dismisses the modal, the a11y label shapes match AC 9, and the existing Story 6.6 character-variant assertions still pass.

### The data `LogEntry`/`BattleHistoryModal` renders (lock onto it — AC 1–6)

`useRoomLogs` (Story 6.5) yields entries from `GET /logs` (Story 6.4 contract). Each entry:

```ts
// shape assumed from Story 6.4 AC 1/9 + Story 6.5 Task 1 — IMPORT 6.5's real exported type
{
  id: string;
  roomId: string;
  eventType: 'character_created' | 'character_updated' | 'character_deleted'
           | 'battle_started' | 'battle_concluded' | 'battle_discarded';
  actorId: string;
  summary: string;          // deterministic plain-text fallback (Story 6.2 buildSummary)
  payload: unknown;         // permissive — Story 6.5 keeps it untyped; 6.6/6.7 narrow defensively
  occurredAt: string;       // ISO-8601 — relative-time source
  createdAt?: string;
  updatedAt?: string;
}
```

For **battle** events, `payload` is the Story 6.3 additive superset; the fields 6.7 reads:

```ts
payload.battle: {
  id: string;                                                       // required for usability
  name: string;                                                     // 6.7 falls back to entry.summary if missing
  status: 'active' | 'concluded' | 'discarded';
  result: 'players_win' | 'monster_wins' | null;                    // meaningful for battle_concluded
  playerSide: { characterIds: string[]; bonuses: BonusItem[] };
  monsterSide: { monsters: MonsterItem[]; bonuses: BonusItem[] };
}
```

- **Battle glyph** = a `Text` rendering `'⚔️'` at the 24×24 row slot (UX 11.4: `⚔️ Battle · Players Win · 8m ago`). No character avatar for battle events (there is no character; the battle is the actor).
- **Battle name** = `payload.battle.name` (fallback to `entry.summary` when absent — Story 6.2's `buildSummary` battle branch reads `Battle '<name>' concluded — <result>` and similar; this is the universal safe fallback for all `LogEntry` branches per 6.6's discipline).
- **Result chip (concluded)** = `'players_win'` → `Players Win` (accent), `'monster_wins'` → `Monster Wins` (danger), missing/`null`/unknown → `Concluded` (textMuted).
- **Discarded label** = the static text `"discarded"` (textMuted); no result chip.
- **Modal participants** = resolve each `playerSide.characterIds[i]` via `useRoomCharacters(roomId)` → `characters.find(c => c.id === id)`; unresolved → `"Removed character"`. **No outbound HTTP to resolve names** (ADR-11; Story 6.3 documented variance — same discipline here).
- **Modal bonuses** = signed: `value >= 0 ? '+'+value : ''+value`.
- **Modal monsters** = `monster.name + ' · Level ' + monster.level`; missing fields → defensive fallback (`Unknown monster` / `Level —`).
- **`summary` strings** come from Story 6.2 `buildSummary` (`Battle '<name>' started`, `… concluded — players win`, `… discarded`) — use as the safe fallback, not the primary render for battle variants (the rich glyph/name/chip UI is the AC).
- **Defensive rule:** `payload` is `unknown` (Story 6.5 keeps it un-narrowed so 6.6/6.7 own narrowing). Treat every `payload.battle.*` access as possibly-absent (a degraded producer or partial event must not crash the list — AC 5). Frontend is **strict TS**: narrow via guards / `typeof` checks, do not blanket-`any`.

> **Variance discipline:** Stories 6.3/6.4/6.5 are `ready-for-dev` (not `done`). These field names are the *documented* contract. **Import 6.5's real exported entry type from `frontend/api/logs.ts`** and conform to whatever 6.5 actually shipped; if a name differs, follow 6.5 and record it in Completion Notes (do not "correct" 6.5/6.3). ### Drill-in design — lead with the clean option (AC 4, 7, 8)

**Recommended: in-place RN `Modal` overlay on the Log screen**, opened by tap from `LogEntry`, rendered from the in-list `payload.battle`. Rationale, in order of weight:

1. **Stories 6.3 / 6.4 explicitly mandate this contract** — both stories' cross-story notes state "battle drill-in renders from the in-list `payload`, no `/logs/:logId` FE caller" ([Source: _bmad-output/implementation-artifacts/6-3-battle-lifecycle-events-are-published-for-room-history.md#Cross-story context] "renders battle history entries and drills into completed battles from the raw stored `payload`"; [Source: _bmad-output/implementation-artifacts/6-4-room-history-api-returns-paginated-events.md#Cross-story context] "drill-in uses the verbatim stored `payload`, not a separate `/logs/:logId` fetch"). The architecture API also provides `GET /logs/:logId` but **no current frontend story consumes it** — adding a FE caller would orphan the established design contract.
2. **No new route** — the architecture explicitly lists `app/munchkin/[roomNumber]/log.tsx` as the only log-related route ([Source: architecture/project-structure-boundaries.md] line 186 "└── log.tsx NEW — Log View"). Creating `log/[logId].tsx` would require restructuring 6.5's flat `log.tsx` into a folder, which violates Story 6.5's already-shipped contract and the minimal-edit rule.
3. **Established in-codebase modal idiom** — [QuickEditSheet.tsx](frontend/components/munchkin/QuickEditSheet.tsx) already uses `Modal transparent={true}` for an in-screen overlay with backdrop dismissal; mirroring this keeps the codebase's modal vocabulary consistent and avoids inventing a new pattern.
4. **Smallest blast radius / cleanest composition** — `LogEntry` adds one optional prop, `log.tsx` adds one state hook + one modal sibling, the new file is one pure-presentational component. No router changes, no deep-link contract, no cache lookup by id.

**Rejected alternative A:** a dedicated dynamic route `log/[logId].tsx` that pulls the entry from the `useRoomLogs` TanStack Query cache. Cleaner on paper (bookmarkable, deep-linkable), but it requires (1) restructuring `log.tsx` → `log/index.tsx` (re-doing part of Story 6.5), (2) a cache-lookup-by-id flow that has no fallback for cold deep-links (since FE intentionally has no `/logs/:logId` fetcher), (3) a new route registration in `_layout.tsx`. No epic AC requires bookmarkability; do not introduce this complexity.

**Rejected alternative B:** reuse the existing `(battle)` modal route. `(battle)/index.tsx` consumes `useRoomBattle(roomId)` which is the **active** battle only — passing a stale concluded battle id would either crash (no active battle returned) or show a confusing empty state. Adapting `(battle)/index.tsx` to handle "active vs historical" battles would balloon scope into Epic 5 territory.

Lead with the modal. Record the decision in Completion Notes.

([Source: architecture/...#frontend layered boundaries]; [Source: _bmad-output/project-context.md] "components stay mostly presentational".)
- **AppTheme tokens only** — pure `StyleSheet.create`, `AppTheme.colors/spacing/radius`; **never** hardcode colors; **never** reference non-existent `AppTheme.typography.body`/`.heading2` (see reality check). Mirror existing components' inline-fontSize-for-body idiom.
- **Expo Router** — `app/**` is route-only; `BattleHistoryModal` lives in `components/munchkin/`, its test alongside it (not under `app/`).
- **Minimal, localized edits** — new `BattleHistoryModal.tsx` (+ optional `logEntryBattle.ts`) + their tests + the **prop+branches additions** to existing `LogEntry.tsx` + the **two-spot** `log.tsx` change. No opportunistic refactor of 6.5/6.6's existing logic, no theme changes, no dependency/lockfile churn, no realtime wiring.
- **Stable rendering** — never throw/blank for any of the 6 supported event types or partial payloads; `summary` is the universal safe fallback (continues 6.6's discipline).
- **a11y** — one descriptive row `accessibilityLabel` per UX-DR12 + the "Double-tap to open battle record" hint for tappable rows; battle glyph hidden from a11y so it doesn't double-announce; close button is a button with a clear label.
- **No outbound HTTP for name resolution** (ADR-11) — character names resolved from `useRoomCharacters(roomId)` only; unresolved → `"Removed character"`.
- **Docs-in-same-change** if a component/route doc exists (Task 6).
